## 📊 核心论点

#### 软件工程的瓶颈已从智能转向人类注意力

- **核心内容**：演讲者提出一个反直觉的观察——当今最优秀的工程师也只能同时推进几个任务，他们可能积压 50 个功能需求，但每天只能向前推进少数几个。原因不在于现有模型不够聪明（模型已能搞定全部 50 个任务），而在于每个 Commit 都需要审查、每个任务都需要监督，人类带宽成为整个系统的限速步骤。Factory 的解题思路是：让人类决定"做什么"，让系统决定"怎么做"，Agent 可以连续工作数小时甚至数天。
- **关键概念**：注意力瓶颈、监督带宽、异步开发、Backlog、Human-in-the-loop
- **实际意义**：这一论断重新定义了 AI 编程工具的目标函数——不再是"让单个 Agent 更聪明"，而是"让人类不在场时系统仍能可靠运行"。这直接指向了从 Copilot 模式向 Autonomous Agent 模式的范式转移，是 Factory、Cognition（Devin）等公司共同押注的方向。

#### 多智能体系统的五种基础协作模式

- **核心内容**：当前多智能体领域术语混乱、框架林立，演讲者提炼出五种前沿模式：（1）**Delegation**：父 Agent 派生子 Agent 完成特定任务，是最简单也最常见的模式；（2）**Creator-Verifier**：实现 Agent 与验证 Agent 分离，由于实现者存在"代码偏爱偏见"，全新上下文的验证者更容易发现问题；（3）**Direct Communication**：Agent 间直接通信无中央协调，但状态会跨对话碎片化；（4）**Negotiation**：围绕共享资源（API、代码区域）协商，最佳场景是正和博弈；（5）**Broadcast**：一对多信息分发，是维持长期一致性的关键。
- **关键概念**：Delegation、Creator-Verifier、Negotiation、Broadcast、Cost Bias、状态碎片化
- **实际意义**：这一分类法为多 Agent 系统设计提供了通用语言。开发者不必再纠结于具体框架的差异，而是可以基于这五种基础模式自由组合。Missions 本身就是 Delegation + Creator-Verifier + Broadcast + Negotiation 四种模式的工程化整合。

#### Missions 三角色架构：Orchestrator、Worker、Validator

- **核心内容**：Missions 不是单个 Agent 会话，而是通过结构化交接和共享状态通信的 Agent 生态。**Orchestrator** 负责规划，作为用户的"思维 sounding board"提出战略问题、生成包含功能、里程碑和验证合约的计划；**Worker** 负责实现，每个 Worker 拿到的都是干净上下文，无累积包袱，读规格、实现功能、Git 提交后让下一个 Worker 继承干净状态；**Validator** 负责验证，不仅跑 lint/类型检查/测试和代码审查，更关键的是验证端到端行为。
- **关键概念**：Orchestrator、Worker、Validator、Clean Context、结构化交接、Validation Contract
- **实际意义**：三角色架构解决了长任务中"上下文污染"和"自我验证偏见"两大顽疾。Worker 的干净上下文设计借鉴了软件工程中的"无副作用函数"思想，Validator 的独立性则借鉴了同行评审的最佳实践，是 Agent 工程化的范本。

#### Validation Contract：先定义对错，再写代码

- **核心内容**：传统编码 Agent 常陷入"自证陷阱"——Agent 写完代码再写测试，测试 100% 通过、覆盖率充足，但测试是被代码塑造的而非被真实需求塑造的，这种验证只是"确认决策"而非"捕获 Bug"。Missions 在规划阶段（任何代码之前）就生成 Validation Contract，独立于实现定义"什么算完成"。复杂项目的合约可包含数百条断言，每个功能被分配一条或多条断言，所有断言之和必须被全部覆盖。
- **关键概念**：Validation Contract、Test-After 反模式、断言驱动开发、规格先行
- **实际意义**：这是对"测试驱动开发（TDD）"思想在 Agent 时代的复活与升级。它解决了 LLM Agent 长任务中最难的"漂移问题"——没有外部锚点的话，Agent 会逐步偏离原始目标。验证合约为长达数天的运行提供了稳定的真理基准。

#### 双层验证：Scrutiny Validator + User Testing Validator

- **核心内容**：每个里程碑后会运行两类验证器。**Scrutiny Validator** 较传统：跑测试套件、类型检查、Lint，并为每个完成功能派生专门代码审查 Agent；**User Testing Validator** 更有趣，它扮演 QA 工程师的角色，启动应用、通过 Computer Use 类技术与之交互——填表单、检查页面渲染、点击按钮、确保功能流端到端工作。后者耗时显著更长，事实上 Missions 的大部分挂钟时间花在等待真实世界执行，而非生成 Token。两个验证器都未事先看过代码，验证天然是对抗性的。
- **关键概念**：Scrutiny Validator、User Testing Validator、Computer Use、对抗式验证、Wall Clock Time
- **实际意义**：这种"行为级验证"是从静态代码分析向动态行为校验的关键跨越。它意味着 Agent 系统的瓶颈正从 Token 生成速度转向真实世界 I/O 延迟，这对底层基础设施（虚拟环境编排、Headless 浏览器、沙箱）提出了新的要求。

#### 串行执行 + 内部只读并行：反直觉的最优策略

- **核心内容**：直觉上 10 个 Agent 并行 = 10 倍吞吐，但 Factory 的实验表明这在软件开发领域不奏效——Agent 之间会冲突、踩踏彼此的修改、做出不一致的架构决策，协调开销吃掉所有收益还烧掉 Token。Missions 选择 Feature 级串行：任意时刻只有一个 Worker 或 Validator 运行；但在 Feature 内部，对只读操作（搜索代码库、研究 API、代码审查等）允许并行。这种"串行 + 定向并行"看似更慢，但错误率大幅下降，长任务下正确性产生复利。
- **关键概念**：Serial Execution、Read-Only Parallelization、协调开销、复利正确性
- **实际意义**：这一发现挑战了"并行即加速"的朴素直觉。它暗示 Agent 系统设计应优先优化错误率而非吞吐量——长时间任务下 1% 的错误率会指数放大，串行执行虽慢但可控，是 Agent 工程化中"正确性优先于速度"的鲜明案例。

#### Droid Whispering：为每个角色配置最优模型

- **核心内容**：规划环节受益于慢速、深思熟虑的推理；实现环节需要快速的代码流畅度与创造力；验证环节则受益于精准的指令遵循。没有任何单一模型或厂商在三方面都最强。Factory 内部把"理解不同 LLM 如何交互、它们在哪里失败、失败如何在多日运行中复合，并审慎决定让哪个模型坐哪个位置"这种新技能称为 Droid Whispering。验证甚至可能用完全不同的厂商以避免训练数据偏见。模型无关架构让你不再被单一厂商最弱能力所限。
- **关键概念**：Droid Whispering、模型路由、模型无关架构、训练数据偏见、复利优势
- **实际意义**：这是对"模型即一切"的有力反驳——架构设计可以让弱模型表现接近前沿模型，而正确的模型路由可以让前沿模型释放更大价值。它也揭示了未来 Agent 公司的竞争壁垒：不是绑定某家模型厂商，而是建立模型无关的工程能力，把模型作为可热替换的组件。

#### 苦涩的教训：用 Prompt 而非硬编码构建系统

- **核心内容**：每个构建多 Agent 系统的人都担心下一次模型发布让架构一夜过时。Missions 的设计原则是：让系统随每次模型升级而变得更好。几乎所有编排逻辑都定义在 Prompt 和 Skill 里，而非硬编码状态机——它如何分解功能、如何处理失败，全部写在约 700 行文本中，改 4 句话就能显著改变执行策略。Worker 行为由 Orchestrator 为每个 Mission 定义的 Skill 驱动。仅有的确定性逻辑很薄，专注于让模型做擅长的事，系统处理记账类工作。
- **关键概念**：Bitter Lesson、Sutton 苦涩的教训、Prompt-as-Code、Agents.md、Skills
- **实际意义**：这是对 Rich Sutton "苦涩的教训"在 Agent 工程领域的具体应用——任何依赖人类先验的硬编码策略，最终都会被更通用的、随计算和数据扩展而进步的方法击败。它给出了 Agent 框架可持续设计的关键准则：把智能留给模型，把纪律留给框架。

## 📝 完整翻译

### (0:00 - 8:00) Part 1

**(0:00 - 1:20)**

大家好，我是 Luke。我的目标是在接下来的 20 分钟里，让你们能够组装出智能体团队，完成比今天单个智能体难度高几个数量级的任务。

先简单介绍一下我的背景。我来自开发工具领域。大约两年半前，我在 Block 公司启动了一个项目，这个项目后来发展成了 Goose。Goose 现在是领先的开源编程智能体之一，最近被捐赠给了 AI 智能体基金会。

现在我在 Factory 工作，负责核心智能体框架的开发。Factory 的使命是为整个软件开发生命周期带来自主性。

**(1:20 - 2:40)**

我想先提出一个观点：如今软件工程的瓶颈不是智能，而是受限于人类的注意力。即使是最优秀的工程师，一次也只能完成几个任务。他们可能有 50 个功能的积压工作，但每天只能推进其中几个，因为每个任务都需要他们的注意力，每次提交都需要他们的审查。

今天的模型足够聪明，能够理解所有这 50 个任务，但没有足够的带宽来监督它们的实施。所以我们一直在问自己：如果人类决定要构建什么，然后系统来解决如何构建，会怎样？智能体可以工作几小时甚至几天，你回来时就能看到完成的工作。

**(2:40 - 3:50)**

这就是我今天要讨论的内容。当你开始研究多智能体框架和系统时，你很快就会意识到这个领域有点混乱。每个人都有自己的框架、自己的术语、自己对什么有效什么无效的看法。

因此，我想提出一个简单的分类法。有五种前沿的多智能体框架：

第一种是委托 (delegation)。这是一个智能体生成另一个智能体，父智能体可能会说"去搞清楚数据库架构"，然后得到回应。这是最简单的多智能体通信形式，也是大多数人首先实现的。子智能体和编程工具是最常见的例子。

第二种是创建者-验证者 (creator verifier)。一个智能体构建某些东西，然后另一个智能体检查这项工作。关键在于关注点分离。实现代码的父智能体有一定的成本偏差，希望代码能正常工作。一个拥有新鲜上下文的新智能体更有可能发现问题，这也是为什么我们人类也要进行代码审查。

**(3:50 - 5:10)**

第三种是直接通信 (direct communication)。这是智能体在没有中央协调器的情况下进行通信，就像互相发私信。但这很难做好，因为在没有协调器的情况下，状态会在对话中分散，没有单一的真相来源。

第四种是协商 (negotiation)。协商是智能体就共享资源进行通信。比如它们想使用同一个 API，或者想修改代码库的同一部分。但协商不一定是对抗性的。实际上，最佳用例是存在净正和交易的情况，即智能体在交互时有潜在的双赢局面。

最后一种是广播 (broadcast)，即一个智能体向多个智能体发送信息。可以理解为状态更新、适用于每个人的新上下文、共享约束。这比其他类型看起来不那么炫酷，但对于维护长期运行任务的一致性至关重要。

**(5:10 - 6:30)**

那么，当你拥有所有这些不同的构建块时，如何将它们组装成一个可以运行多天的系统呢？

Missions 是我们的答案。它是一个将其中四种（委托、创建者-验证者、广播和协商）结合到单一工作流程中的系统。你描述一个目标，通过对话确定范围，批准一个计划，然后系统处理数小时或数天的执行，让你能够专注于其他事情。

值得注意的是，Mission 不是单个智能体会话，而是通过结构化交接和共享状态进行通信的智能体生态系统。它使用三角色架构：编排器 (orchestrator)、工作者 (worker) 和验证者 (validator)。

编排器处理规划。当你描述你想要什么时，编排器就像你的智囊团，会问你正确的战略问题，检查问题空间中是否有任何不明确的需求，然后最终产生一个包含功能、里程碑以及验证合同的计划。验证合同定义了在任何编码完成之前"完成"的含义。

**(6:30 - 8:00)**

第二个角色是工作者，它们处理实现。当功能分配给工作者时，该工作者有干净的上下文，没有累积的包袱，没有衰减的注意力。工作者阅读其规范，实现功能，然后通过 Git 提交，让下一个工作者继承干净的状态和可工作的代码库。

最后一个角色是验证者，它们处理验证。大多数系统通过运行 lint、类型检查、测试进行验证，可能还会做代码审查。Missions 做所有这些，但我们还验证行为。我们不只是问代码看起来是否正确，而是问这是否端到端地工作。正是这种差异让 Missions 能够连续运行多小时、多天而不偏离轨道。

让它工作需要完全重新思考验证。当你之前使用编程智能体时，你可能见过这种模式：智能体构建一个功能，编写一些测试，测试通过，有完整的覆盖率。但测试是由代码塑造的，而不是由代码实际试图做的事情塑造的。实现后编写的测试不会捕获 bug，它们只是确认决策。如果你依赖这样的验证，你的系统最终会偏离轨道。

这就是为什么存在验证合同。它在规划期间编写，在任何代码之前，独立于实现定义正确性。对于复杂项目，这可能是数百个断言，每个功能都分配一个或多个必须满足的断言。所有功能的总和必须意味着每个断言都被覆盖。

### (8:00 - 16:00) Part 2

**(8:00 - 9:00)**

验证者之前从未见过这些代码。他们对具体实现没有投入，所以验证本质上是对抗性的设计。
